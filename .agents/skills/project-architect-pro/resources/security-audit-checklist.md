# ✅ چک‌لیست ۳۵ موردی ارزیابی معماری و امنیت سیستم (Security & Architecture Checklist)

قبل از استقرار و انتشار هر سیستم، این ۳۵ شاخص امنیتی و ساختاری را بررسی کنید:

## ۱. مدیریت متغیرها و کلیدهای محرمانه (Secrets & Env)
- [ ] هیچ کلید API، توکن، پسورد یا کانکشن‌استرینگ به صورت هاردکد در کد وجود ندارد؟
- [ ] فایل `.env` در فایل `.gitignore` قفل شده و کامیت نشده است؟
- [ ] فایل `.env.example` با متغیرهای لازم و بدون مقادیر حساس در ریشه پروژه وجود دارد؟
- [ ] متغیرهای فرانت‌اند (مثل `VITE_` یا `NEXT_PUBLIC_`) حاوی کلیدهای سروری یا محرمانه نیستند؟
- [ ] کلیدهای JWT و کلیدهای هش از رشته‌های تصادفی با انتروپی بالا (حداقل ۲۵۶ بیت) ساخته شده‌اند؟

## ۲. احراز هویت و توکن‌ها (Authentication & JWT)
- [ ] کلمات عبور با الگوریتم‌های استاندارد (Bcrypt با دور ۱۲+ یا Argon2id) هش می‌شوند؟
- [ ] توکن‌های احراز هویت در کوکی‌های امن با فلگ‌های `HttpOnly`, `Secure`, `SameSite` ذخیره شده‌اند؟
- [ ] زمان انقضای Access Tokenها کوتاه (۱۵ الی ۳۰ دقیقه) تنظیم شده است؟
- [ ] مکانیزم باطل‌سازی یا بلک‌لیست برای توکن‌های Refresh هنگام خروج کاربر وجود دارد؟
- [ ] مسیرهای لاگین و بازیابی رمز عبور مجهز به محدودساز نرخ درخواست (Rate Limiting) هستند؟
- [ ] بعد از چند تلاش ناموفق پیاپی برای ورود، حساب به صورت موقت قفل می‌شود؟

## ۳. کنترل دسترسی و سطوح کاربری (Access Control & RBAC)
- [ ] تمامی اندپوینت‌های حساس در بک‌اند سطوح دسترسی (Role-based / Permission-based) را بررسی می‌کنند؟
- [ ] از آسیب‌پذیری BOLA / IDOR با بررسی مالکیت رکوردها توسط کاربر جاری جلوگیری شده است؟
- [ ] عملیات تغییر یا حذف داده‌ها همیشه با متدهای امن (POST, PUT, DELETE) و پس از اعتبارسنجی انجام می‌شود؟
- [ ] کاربران معمولی به مسیرها یا APIهای ادمین تحت هیچ شرایطی دسترسی ندارند؟

## ۴. اعتبارسنجی و پاک‌سازی ورودی‌ها (Input Validation & Injection Defense)
- [ ] تمامی ورودی‌ها (Body, Params, Query) توسط شمای سخت‌گیرانه (Zod, Joi, Pydantic) اعتبارسنجی می‌شوند؟
- [ ] کوئری‌های دیتابیس صرفاً از طریق ORM یا پارامتریک (Parameterized Queries) اجرا می‌شوند (نه با الحاق رشته)؟
- [ ] در فرانت‌اند از رندر مستقیم HTML ورودی کاربر بدون کتابخانه `DOMPurify` خودداری شده است؟
- [ ] اعتبارسنجی فایل‌های آپلودی از نظر نوع فایل (MIME Type)، اندازه و نام رندوم انجام می‌شود؟
- [ ] از آسیب‌پذیری پیمایش مسیر (Path Traversal) در خواندن فایل‌ها جلوگیری شده است؟

## ۵. هدرهای امنیتی و تنظیمات مرورگر (Security Headers & CORS)
- [ ] هدرهای امنیتی (Helmet یا معادل آن) در سرور فعال هستند؟
- [ ] سیاست امنیت محتوا (Content-Security-Policy) به درستی پیکربندی شده است؟
- [ ] سیاست CORS صرفاً دامنه‌های مجاز و مشخص را قبول می‌کند (`origin: '*'` حذف شده است)؟
- [ ] هدر `X-Frame-Options: DENY` یا `SAMEORIGIN` برای جلوگیری از Clickjacking فعال است؟
- [ ] اجبار اتصال HTTPS از طریق هدر `Strict-Transport-Security (HSTS)` تنظیم شده است؟

## ۶. پاسخ‌های خطا و لاگ‌گیری امن (Error Handling & Safe Logging)
- [ ] پیام‌های خطای کلاینت حاوی جزئیات دیتابیس، استک‌ترس (Stack Trace) یا مسیر فایل‌های سرور نیستند؟
- [ ] اطلاعات حساس کاربران (کلمات عبور، شماره کارت، توکن‌ها) در لاگ‌های سرور چاپ نمی‌شوند؟
- [ ] خطاهای پیش‌بینی‌نشده توسط یک Global Error Handler مرکزی مدیریت و لاگ می‌شوند؟
- [ ] لاگ‌های رویدادهای امنیتی (تلاش برای لاگین، تغییر رمز، حذف حساب) با زمان دقیق ثبت می‌شوند؟

## ۷. ساختار معماری و تمیزی کد (Architecture & Clean Code)
- [ ] تفکیک وظایف (Separation of Concerns) بین لایه‌های UI، منطق تجاری و دسترسی به داده رعایت شده است؟
- [ ] پوشه‌بندی پروژه منظم و ماژولار بوده و فایل‌های God File (بیش از ۵۰۰ خط نامربوط) شکسته شده‌اند؟
- [ ] ایمپورت‌ها از طریق Path Aliasهای استاندارد (`@/components`, `@/services`) مرتب شده‌اند؟
- [ ] پکیج‌ها و کتابخانه‌ها به صورت منظم با `npm audit` یا `pip-audit` از نظر آسیب‌پذیری اسکن شده‌اند؟
- [ ] مستندات ساختار پروژه (`ARCHITECTURE.md` یا `README.md`) به‌روزرسانی شده است؟
